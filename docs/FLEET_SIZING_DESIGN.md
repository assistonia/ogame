# 공격 편대 사이징 재설계 (레이더 키스톤) — 설계

작성 2026-07-12. 사용자 승인: "편대 사이징을 키스톤으로, 재정렬." 관련: [[COMBAT_AND_AI_GAP_TASKS]].

## 배경 / 문제
- `ATTACK_FIGHTERS = 4` (raider.py:201). 겁쟁이(방어0) 게이트와 카나리(EV) 경로 **모두**
  `_attack_force`로 편대를 만들고, 거기서 전투기는 `min(보유, 4)` 고정.
- 귀결: (a) 큰 전투 함대(ai01 전투기 530)가 **어떤 공격에도 안 쓰임** → 영구 실업, (b) 방어 있는
  타겟은 4대로 못 이겨 영원히 회피, (c) **B(카나리 확대)를 열어도 시뮬이 4대로 평가**하니 실익 미미.
- 목표: 편대를 **타겟 방어에 비례해 사이징** → 큰 함대가 요새를 순EV 양수로 공략. 그래야 B가 실효.

## 전제조건 감사 (2026-07-12 코드 실측 — 설계 허수 방지)
- **데브리 항 (조건3): 이미 구현.** `battle_sim.simulate`→`expected_debris(m,c)`(격파 함선 30%,
  방어시설 제외). `attack_ev = win×loot + 데브리(리사이클러 없으면 ×0.3) − attacker_loss_value`.
  → 사이징은 `attack_ev`를 **재사용**만 하면 데브리 자동 반영. 빼먹지 말 것.
- **리사이클러 수거 배선: 있음.** `find_debris_targets`+`_queue_recycler_build`+HARVEST 미션(로그
  `raid HARVEST 리사이클러2 데브리~50400`). has_recycler=True 전제 성립.
- **연료(듀테륨) 항 (조건1): 없음.** `attack_ev`에 왕복연료 차감 부재. **신규 추가 대상.**
- **섀도/로그 게이트 (조건4): 있음.** `_battle_sim_shadow(mode=log)` + `battle_guard.record_prediction`
  /`reconcile`가 예측을 실제 battle_report와 대조. 단 아래 §5 주의(섀도는 사이징 편대를 실제로
  보내지 않으므로 "사이징 편대의 실측"이 아니라 "sim 엔진 정확도"를 검증).
- **max_active (조건2): 있음(raider.py:1122 "진행중 함대 N건 → idle").** 편대 크기 상한과 직교.

## 설계 결정 (조건 1~5)

### 1. 마진 기반 티어 선택 (★ 최우선)
- `_attack_force` 단일 대신 **후보 편대 티어**를 생성: 보유 전투함대의 예: {20%, 40%, 60%} 규모 +
  약탈 맞춤 카고. 각 티어를 `battle_sim.decide`로 시뮬.
- 선택 기준 = **순EV 최대**: `win×loot + 데브리 − 자기손실 − 왕복연료`. "이길 최소 함대" 금지.
- 이유: 시뮬 ±오차 + 방어 70% 복구 + 정찰 시차(정찰 후 방어 증설 가능) → 최소치는 확률적으로
  짐. 오버킬 마진이 EV 극대화에서 자연 발생하게 둔다(win_threshold 유지, 그 위에서 순EV 최대).

### 2. 상한: 상수 → 비율
- `ATTACK_FIGHTERS=4` 교체: **1회 출격 ≤ 보유 전투함대의 60~70%.** 전량 출격 금지 —
  시뮬 오차로 전멸하는 걸 막는 마지막 안전핀 + 집에 남은 함대는 플릿세이브가 커버.
- `max_active`(동시 임무 수)와 직교하므로 그대로 공존. 기존 "3건 이상 휴식" 게이트 앞단 유지.

### 3. 데브리 항: 유지 (이미 있음)
- `attack_ev`의 `expected_debris` 그대로. 사이징이 큰 편대를 뽑으면 격파량↑→데브리↑ 자동 반영.
- has_recycler=False면 ×0.3 할인 유지(전제조건상 raider는 리사이클러 보유가 정상 경로).

### 4. 연료 항: 신설
- `attack_ev`에 **왕복 듀테륨 비용 차감** 추가. 편대 소비연료 = f(거리, 함선 추진, 속도).
- 없으면 큰 편대를 원거리 타겟에 몰빵하는 왜곡. 티어 비교의 필수 항(작은 티어가 연료로 이길 수 있음).

### 5. 배포: 섀도 우선 (기존 게이트 재사용)
- 사이징 로직도 `mode=log`(SHADOW): 실제 공격은 **기존 4대 편대가 계속** 나가고, "사이징이라면
  이 편대·이 순EV"를 로그.
- **주의(정직)**: 섀도는 사이징 편대를 실제로 보내지 않으므로 "사이징 편대의 실측 회수"는 못 잰다.
  대신 `battle_guard.reconcile`로 **sim 엔진 자체의 예측 정확도**(보낸 4대 편대의 예측 vs 실제)를
  며칠 채점 → 엔진이 정확하면 더 큰 사이징 편대도 신뢰 가능. 이게 "요새 자살" 방지의 근거.
- 통과하면 ai01 사이징 라이브 → raider AI 전원 → 규칙 레이더 (= 기존 B 확대와 자연 연결).

### 6. 카고: 사이징에 흡수 (별도 가드 X)
- "카고 누수 아님" 판정 수용(측정: 실약탈은 카고 상한 안 걸림). 편대 생성 시 카고 =
  `min(보유, ceil(loot/적재))`로 포함. 부족 시 **"카고부족으로 EV 깎임" 사유 로그만**(침묵 추적).

## 배포 순서 (기존 B 계획과 통합)
1. `attack_ev`에 연료 항 추가 + 티어 사이징 함수 신설 → **SHADOW 로그** (4대 라이브 유지).
2. `battle_guard.reconcile`로 sim 정확도 며칠 채점.
3. 통과 → ai01 사이징 라이브 24h 관찰 → raider AI 전원 → 규칙 레이더.
   (관찰지표: 약탈 회수율, 함대 손실 vs 시뮬 오차, 피격 채굴러 A반응.)

## ⚠ 예고: 터틀 손익분기 시험 (72h 분석의 하이라이트)
- 사이징이 켜지면 "전투기 200대면 뚫리고 순EV 양수인 요새"가 처음으로 **공격 대상**이 됨.
  지금까지 터틀 방어(예: 3,155기)는 "4대 편대는 못 뚫는 벽"이라 절대안전이었음 — 그 가정이 깨짐.
  방어 도배 vs 대편대의 실제 손익분기가 데이터로 나옴.
- **선행조건**: A(피격 반응)의 "**터틀 피격 시 방어 재건 우선순위 상향**"이 배선돼 있어야 터틀이
  무저항 붕괴하지 않는다. 현 상태: [[COMBAT_AND_AI_GAP_TASKS]] A 스펙에 포함(적응 단계), **미구현.**
  → 사이징 라이브(3단계) 전에 터틀 재건 반사도 함께 배선할 것.

## 구현 상태 (2026-07-12 — LIVE)
- **사이징 섀도 구현+활성**: raider.py/battle_sim.py(연료항+티어생성기+65%상한).
  사이징 live는 OFF이며 기존 공격력 생성기를 유지한다. 다만 모든 공격은 새 보고서+24h 합법 정찰 peak,
  계정 전체 함대가치의 15%(절대 하한 50k)인 동적 위험 한도, ETA 75초 preflight를 통과해야 한다.
  고정 100k의 v1과 동적 한도의 v2 exact-match cohort는 섞지 않는다. universe.log에
  `[sizing/shadow]` 로그 실측 확인. 무방비→LF1, 요새→tier80=none/음수EV(정확 회피), 일부 티어분화.
  바퀴 82→96s(+14s CPU, 인터벌 240s 대비 여유).
- **터틀 반사 LIVE**: threat.py(신규)+turtle.py. `TURTLE_REFLEX_ENABLED=True`.
  상태트리거(방어<피크)+배틀리포트 폴백. 첫 관측은 baseline만 저장한다.
- **관측 리파인 후보(비블로커)**: 섀도가 라이브 레이더의 zero-defense 우선 타겟을 평가 →
  요새는 무방비 후보가 없는 틱에만 기회적으로 평가됨. 요새 격파 데이터를 체계적으로 모으려면
  틱마다 "최고가치 방어 타겟"도 함께 평가하는 확장 고려(데이터 축적엔 지장 없어 후순위).

## LIVE 플립 시 부하 계약

- 현재 `_sizing_shadow_log`는 tier를 모두 계산하고도 로그 문자열만 반환한다. LIVE 구현은 이를
  구조화된 `selected_fleet/decision/log` 반환으로 바꾸고 **그 동일 객체를 집행**해야 한다.
- preflight 뒤 tier를 다시 계산하는 이중 경로는 금지한다. 정찰 스냅샷과 집행 편대의 exact-match
  계약도 깨지고, 측정상 바퀴당 보통 1.3~5.7초(heavy burst 약 10초)를 중복 소비한다.
- 결과 재사용 기준 LIVE 총 증분 예산은 공격/수거 I/O 포함 +3~10초/바퀴다. 이중계산 시
  +5~20초/바퀴로 본다.
- 최근 15개 완주 바퀴 p90 150초가 용량 경보다. 경보는 interval/플래그를 자동 변경하지 않으며,
  현재 4분 start-to-start를 유지할지 사람이 검토하는 트리거다.

## CPU 격리 v1 (2026-07-13)

전투 공식·후보 16단계·표본수(12/24)·고정 seed(1234)·승률/EV 게이트는 변경하지 않고
계산 배선만 최적화한다.

- `battle_cache.py`가 함수 종류와 양측 편대/연구, 약탈량, recycler, mode, samples, seed를 모두
  canonical JSON으로 만든 SHA-256 content key로 사용한다. cache miss는 기존 `simulate/decide`를
  그대로 호출하며, 동일 key의 동시 miss는 한 스레드만 계산한다. 결과는 복제해 호출자 변경이
  다음 hit를 오염시키지 않는다. 전투 공식을 바꾸면 `CACHE_ENGINE_VERSION`을 반드시 올린다.
- preflight 운영 경로의 관측용 shadow는 pending 공격, stale/partial intel, 가치·공격·정찰
  cooldown, 부족한 정찰기 등 cheap gate를 먼저 통과한다. 그 뒤에도 계정/240초 bucket/좌표/report
  id의 결정적 1/64 표본에서만 계산한다. ThreadPool 완료 순서에 따른 무작위 편향이 없다.
- 이 budget은 **관측용 shadow에만** 적용된다. 새 preflight 보고서가 도착한 실제 공격 후보의
  `_autonomous_sized_attack`과 최종 EV 판단은 항상 실행된다. legacy/canary의 집행 판단도 budget을
  타지 않는다.
- 발사 직전 최신 합법 보고서를 다시 읽어 평가한 report id/created_at과 exact-match인지 확인하고,
  24h 정찰 peak, 현재 행성 보유함대, 공격/전체 슬롯, cooldown, 가치, 승률·EV를 다시 확인한다.
  변경되거나 조회할 수 없으면 발사하지 않는다. 동일 내용이면 exact cache hit라 재검증 CPU는 작다.
- 수동 microbench: `python3 tests/bench_battle_cache.py`. 기준 fixture에서 cold 16개 sizing miss와
  20회 warm 반복의 평균시간, miss/hit 수를 함께 출력한다. 정합성·stale invalidation·동시 dedupe는
  `tests/test_battle_cache.py`와 `tests/test_raider_preflight.py`가 고정한다.
